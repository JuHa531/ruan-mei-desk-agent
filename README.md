# 梅梅 · 本地 AI Agent

一个完全本地运行的桌面 AI Agent：Ollama 对话、工具调用、PyWebView2
三栏界面、离线语音合成与识别、背景/表情素材、提醒与日程、Office/视频生成，
以及通过 Windows SMTC 在后台控制 QQ 音乐。

本仓库是源码分发版。个人习惯、提醒、听歌记录、日志、浏览器缓存、
大型背景视频和模型权重不会提交；完整清单与恢复方式见
[`docs/FILE_MAP.md`](docs/FILE_MAP.md) 和
[`docs/ASSETS_AND_PRIVACY.md`](docs/ASSETS_AND_PRIVACY.md)。

面向这台机器：RTX 4060 Laptop（8GB 显存）+ 32GB 内存 + i7-14650HX，所有大文件放 G 盘。
目标是从零做出一套**完全离线、不依赖任何 API**、并且用你自己数据微调过的 AI。

全套流程大约需要两天，其中真正点鼠标的部分只有几个小时，其余时间在等下载和等训练。

> **两个专项文档**：想让 AI 用指定音色说话看 [VOICE.md](VOICE.md)；

## 阶段 1：本地推理跑通

### 1.1 装 Ollama

从 https://ollama.com/download 下载 Windows 安装包。默认会装到 C 盘的用户目录（程序本体不大，几百 MB），**模型才是大头，而模型已经被环境变量指到 G 盘了**，所以没问题。

装完验证：

```powershell
ollama -v
```

### 1.2 拉一个中文模型

```powershell
ollama run qwen3:8b
```

第一次跑会下载约 5GB。跑起来后可以直接在命令行聊天，输入 `/bye` 退出。

8GB 显存下这几个都合适：

| 模型 | 大小 | 特点 |
|---|---|---|
| `qwen3:8b` | ~5GB | 中文最强，日常首选 |
| `qwen3:4b` | ~2.6GB | 更快，显存宽裕，适合做微调的基座 |
| `deepseek-r1:7b` | ~4.7GB | 推理链明显，适合数学/逻辑 |

### 1.3 接一个界面（可选但强烈建议）

命令行聊天不好用，装个网页界面：

```powershell
pip install open-webui
open-webui serve
```

浏览器打开 http://localhost:8080 就能用了。Open WebUI 还自带知识库（RAG）功能，把文档丢进去它就会检索后回答——**这一步就能实现很多人口中「懂我的 AI」，而且完全不用训练**。

想让 AI 帮你写代码，装 VS Code 的 Continue 或 Cline 插件，模型选 Ollama 即可。

### 1.4 断网验证

把网断了，再问它一个问题。能正常回答，就说明你已经有了一套不依赖 API 的本地 AI。

**到这里如果已经够用，后面可以不做。** 继续往下是因为你想让它更像你。

## 阶段 2：准备训练数据

### 2.1 先想清楚你要哪一种

| 你的诉求 | 用哪条路 | 需要的数据 |
|---|---|---|
| 它不懂我的资料 | RAG，不训练 | 文档丢进 Open WebUI 知识库 |
| 它要记住关于我的事实 | 系统提示词 | 几段描述写进 Modelfile 的 SYSTEM |
| 它说话要像我 | 续写式微调（路线 A） | 你写过的文字，**不需要标注** |
| 它要按我的固定格式/流程干活 | 指令式微调（路线 B） | 「输入 → 期望输出」成对，200 条起 |

先别急着选路线 B，它的成本是路线 A 的好几倍。

### 2.2 路线 A：续写式（把原始笔记直接变成数据集）

这条路的优点是不需要人工标注——你写的文字本身就是训练数据。

准备一个 `.md` 或 `.txt`，里面放你写的笔记、邮件、总结，越多越好（有几万字就够跑一轮）。仓库里放了一个样例：`data/template_notes.md`。

转换并体检：

```powershell
python scripts\prepare_data.py completion --src data\template_notes.md --out G:\ai\data\style.jsonl
```

**注意**：这条路线学到的是**语气和表达习惯**，模型不会因此记住笔记里的具体事实。想让 AI 知道你养了猫，那件事要写进系统提示词。

### 2.3 路线 B：指令式（需要你自己写答案）

格式是每行一个 JSON：

```json
{"instruction": "同事提出把交付提前两周，你怎么看？", "output": "不现实。测试最少三周，压到两周等于砍掉回归测试……"}
```

`data/template_instruction.jsonl` 里有 4 条真实可用的示例，照着改。

收集方法建议：

1. 正常用阶段 1 的模型一周，把「答得不像我」的场景记下来
2. 每个场景写下你自己会怎么回答——**这就是一条样本**
3. 攒到 200 条左右再开训，不要攒到 20 条就急着跑

写完先做体检，这一步能省掉大量白跑的时间：

```powershell
python scripts\prepare_data.py check --src G:\ai\data\train.jsonl
```

它会报出样本数、长度分布、重复率，并给出「该不该训」的建议。

### 2.4 数量门槛

| 数据量 | 效果 |
|---|---|
| < 50 条 | 别训，不如把系统提示词写好 |
| 100~300 条 | 能稳定改变语气和输出格式 |
| 500~2000 条 | 能学会一类任务，性价比最高的区间 |
| 5000+ 条 | 能学复杂领域行为，但清洗成本很高 |

**200 条高质量 > 2000 条低质量。** 质量指：格式一致、长度相近、不互相矛盾、覆盖典型场景。

## 阶段 3：微调

### 3.1 建训练环境

环境已装好并验证通过，位于 `D:\ai\envs\llm`（2026-10-08）。要重建的话：

```powershell
conda create -p D:\ai\envs\llm python=3.12 -y
conda activate D:\ai\envs\llm
pip install torch==2.14.1+cu130 torchvision==0.29.1+cu130 --index-url https://download.pytorch.org/whl/cu130
pip install numpy unsloth -i https://pypi.tuna.tsinghua.edu.cn/simple
```

三件事一定注意，都是实际踩过的坑：

- **环境放 D 盘**，不要放 G 盘。G 盘是 USB 机械硬盘（实测写 84 MB/s），装环境慢好几倍，训练中途被拔掉还会损坏环境
- **`HF_ENDPOINT` 必须设成 `https://hf-mirror.com`**，否则 `huggingface.co` 连不上（实测 15 秒超时），模型下不下来
- **用国内镜像装 unsloth 会把 torch 换成 CPU 版**，装完必须自检，被换了就重跑上面那条 torch 命令

自检的两条命令都必须通过才算环境可用：

```powershell
D:\ai\envs\llm\python.exe -c "import torch; print(torch.__version__, torch.cuda.is_available(), torch.cuda.get_device_name(0))"
D:\ai\envs\llm\python.exe -c "import torch, bitsandbytes as bnb; m=bnb.nn.Linear4bit(128,128,bias=False,quant_type='nf4',compute_dtype=torch.float16).cuda(); print('4bit OK', m(torch.randn(4,128,device='cuda',dtype=torch.float16)).shape)"
```

期望输出 `2.14.1+cu130 True NVIDIA GeForce RTX 4060 Laptop GPU` 和 `4bit OK torch.Size([4, 128])`。

只确认 `is_available` 是不够的——QLoRA 真正依赖 4bit 量化，那条命令才是关键。

### 3.2 开跑

```powershell
D:\ai\envs\llm\python.exe scripts\train_qlora.py --data G:\ai\data\train.jsonl --out G:\ai\out\run1
```

默认参数已经按 8GB 显存调好：4bit 量化、batch=1、梯度累积 8、序列长度 2048、LoRA r=16。

训练过程中盯两个数：

- `loss` 应该稳步下降，降到 1.0 以下通常说明学到东西了
- 验证集的 `eval_loss` 如果开始回升，说明过拟合了，减少 epoch 或加数据

**报 CUDA out of memory 怎么办**（8GB 很常见，不是你的问题）：

```powershell
# 按这个顺序依次试，每次只改一个
--max-seq-length 1024
--lora-r 8
--model unsloth/Qwen3-1.7B-unsloth-bnb-4bit
```

另外训练前把浏览器、游戏、其他占显存的程序全关掉，8GB 里那点余量很关键。

### 3.3 想换基座模型

```powershell
--model unsloth/Qwen3-8B-unsloth-bnb-4bit    # 效果更好，但 8GB 是极限，容易 OOM
--model unsloth/Qwen3-4B-unsloth-bnb-4bit    # 默认，稳
--model unsloth/Qwen3-1.7B-unsloth-bnb-4bit  # 最快，适合先把流程跑通
```

第一次训练建议先用 1.7B 跑通全流程（20 分钟出结果），确认每一步都对，再换 4B 正式跑。

## 阶段 5：验证与迭代

训练完不要只问一句「你好」就觉得成了。用一份固定的测试清单：

准备 15~20 个问题，覆盖你训练时想解决的场景，**外加 5 个和训练无关的普通问题**（比如「解释一下什么是光合作用」）。

对比同一份清单在「微调前」和「微调后」的回答。如果第二类问题上明显变笨了，说明**灾难性遗忘**——数据太窄了，往回掺几百条通用问答数据再训一次。

迭代节奏建议：小步快跑。改一次数据训一轮，跑测试清单，记录变化，再改。每次只动一个变量，否则你不知道是哪个改动起的作用。

## 阶段 6：让它出声（可选）

想让 AI 用指定音色把回复读出来——比如某个角色的声线，或者你自己的声音——见单独的文档：[VOICE.md](VOICE.md)。

一句话概括：语音是一层独立的模块，接在模型后面，**不需要重新训练模型**。适配器脚本已经写好并通过了端到端测试，在 [voice/tts_server.py](voice/tts_server.py)。

唯一要注意的是显存：8GB 装不下 8B 模型加语音模型，换 4B 对话模型就宽裕了。

**想让同一个音色表达不同情绪**（开心、生气、难过……）需要换成 IndexTTS2，它能
把音色和情绪分开控制，支持八维情绪向量和「用一句话描述情绪」。适配器和后端封装
都已写好，细节和显存权衡见 [VOICE.md](VOICE.md) 的情绪控制那一节。

### 流式朗读：边生成边读

最早的做法是「等整段回复写完 → 整段合成 → 播放」，长回复要等十几秒才开口。
现在改成流式：回复还在生成时，就按句切块送合成，边合成边播。

四个关键点（都在 `app/agent.html` 的流式朗读那一段）：

1. **第一块只要第一句**，后面的按 60 字打包——开口快最重要，接缝少次之；
2. **允许 2 段同时合成**，一段播完下一段已经准备好了，中间不断；
3. **按序号保序播放**：先合成完的不一定先播，顺序必须跟文字一致；
4. **避开代码块**：切块时不切在未闭合的 ``` 里面，否则前后半截分别送出去，
   清理逻辑认不出整块代码，会把代码念出来。

实测（回复 120 字，切成 3 块）：

| 方式 | 第一声在第几秒 |
|---|---|
| 老逻辑（整段合成，实测 8.3 秒） | 约 10.4 秒（生成 2.1s + 合成 8.3s） |
| 流式（第一块只有 28 字） | **3.0 秒** |

切块拼回去与原文字字相同（做过校验），队列播完会自动清状态。

### 朗读缓存：为什么「重播」不该再合成一遍（2026-10-12）

用户报的现象：自动朗读读完一次之后，点「重播」会**再合成一遍**（再打一次 `/api/tts`，
等好几秒）。同一句话读第二遍却要重新算，确实很蠢。

现在按「语气 + 文本」缓存，两种形态：

| 形态 | 什么时候产生 | 播的时候 |
|---|---|---|
| `kind:'url'` | 整段模式合成出来的 wav | 原来的 `<audio>` 元素 |
| `kind:'buffer'` | 流式朗读读完，把每一块**按序拼成一条** AudioBuffer | Web Audio 直接播，零等待 |

几个细节：

* 缓存满了（12 条）丢最久没用的那条，并 `revokeObjectURL` —— 以前的写法从来不释放，
  每点一次重播就多占一份 wav 内存。
* 拼条时按 `sp.decoded` 里**真实存在的序号**取块，不是按 `sp.seq` 数数 ——
  中间有块合成失败也能拼（跳过那块），否则整条缓存都会失败。
* 块与块之间补上和播放时一样的停顿（`SP_SEAM`），重播听起来才跟第一次一致。

实测（`scripts\check_voice_cache.mjs`）：第一次点重播 → `/api/tts` 调用 **1** 次；
再点一次 → 新增 **0** 次（走缓存）；流式读完 → 缓存里出现 `kind:"buffer"` 的那条。

### 朗读时让背景视频让路

现象：回答的那十几秒里背景视频一顿一顿。原因是语音合成和背景视频**都要用显卡**
（合成是重头），两件事抢同一块 GPU。做法是朗读期间把那两个 `<video>` 按暂停，说完自动接着放：

* 用"代次"（`bgToken`）而不是计数器：新一轮朗读把代次加一，上一轮留下的延时恢复任务
  发现代次变了就不动手 —— 否则很容易出现"刚开始念下一句、上一句的定时器把背景又放开了"。
* `loopGuard()` 里那两个"被暂停/卡住就重新播放"的钩子要认 `dataset.hold`，
  不然它会把我们故意按下的暂停又抢着叫醒。
* 外观面板里有开关（默认开）：「朗读时让背景视频停一下（防卡顿）」。

实测：点击后 200ms / 500ms 采样，背景视频是 `paused:true, hold:"1"`；念完恢复
`paused:false, hold:""`。

#### 接缝为什么曾经听着卡（重要）

**先看这个：模型会偶发截断，这才是"突然中断"的主因。**

同一句话（89 字）重复合成，有时只出 3 秒音频（本该 25 秒），念了开头就没了。抽样实测：

| repetition_penalty | 正常 | 截断 |
|---|---|---|
| 1.35（上游默认） | 9/12 | **3/12** |
| 1.15 | 11/12 | 1/12 |
| **1.0（现在）** | **12/12** | 0/12 |

改成 1.0 之后又跑 6 次，全部 24~26.6 秒、语速稳定 3.4 字/秒。
另外**长文本更容易被严重截断**：89 字一次性合成只出 3.6 秒（13%），
所以必须靠 `cut2` 每 50 字切一块，不能图省事改成 `cut0`。

适配器里还加了一层兜底（`max_retry`）：合成结果短于「字数 ÷ 6 秒」就判定为截断，
自动重试最多 3 次、取最长的那次。模型偶发抽风挡不住，这层能压住。

第一版流式听着「断句和呼吸不自然」，原因不在加载速度——实测 `<audio>` 换源只花 0.03 秒。
真正的问题是**每段音频自带的头尾静音**没处理：

| 项目 | 实测值 |
|---|---|
| 每段音频头部静音 | 0.05 ~ 0.17 秒（每段不一样） |
| 每段音频尾部静音 | 0.35 秒（后端 `fragment_interval` 留下的） |
| 于是老方案的每个接缝 | 0.43 ~ 0.52 秒**不等**的静音，还夹着两次换气 |

现在：**掐掉头尾静音（各留 15ms）**，接缝设为固定 0.32 秒——和后端句内停顿 0.35 秒对齐，
听感一致。播放改用 **Web Audio 精确排期**，块与块之间是采样级连续，不再"播完再加载下一段"。
实测每个接缝都精确等于 0.320 秒，说明没有一块在等合成。

块大小也不是固定的：合成速度约是播放速度的 2.5 倍，所以**下一块最多比上一块大 2.5 倍**
才不会「上一块播完了、下一块还在合」。代码里按 1.8 倍逐块放大（留余量），
实测 18 → 32 → 47 → 63 字。

**还是嫌接缝明显的话**：界面「外观」里有个「分块朗读」开关，取消勾选就变成整段一次性合成
——没有任何接缝、最连贯，代价是长回复要等十几秒才出声（实测 170 字回复：整段模式第一声
6.6 秒，分块模式 3~6 秒）。两种模式的差别就是「开口快」和「零接缝」的取舍。

## 阶段 7：让它会看图

### 一个把流式语音全废掉的坑：start() 的单位

```js
src.start(at, start, dur)   // ← start / dur 的单位是「秒」
```

`trimSilence()` 返回的是**采样索引**，直接当秒传进去，等于让播放从"第 34858 秒"开始——
远远超出音频长度，**整块放出来是静音**。表现极具迷惑性：

- 自动朗读没声音，**点「重播」才有**（重播走 `<audio>` 元素，不受这个影响）；
- 偶尔又能听到一句——那是不带前导静音、`start == 0` 的那一块。

验证方法（别靠听）：用 `OfflineAudioContext` 把同样的排期渲染一遍，量输出音量。

| 文本 | 前导静音(采样) | 修复前 RMS | 修复后 RMS |
|---|---|---|---|
| 看起来你的 GPU 可能没有被正确识别… | 34858 | **0** | 0.079 |
| 你可以尝试重新安装 NVIDIA 驱动程序… | 77660 | **0** | 0.084 |
| 另外，也可以查看是否有其他进程占用… | 12728 | **0** | 0.066 |

### agent 能力：工具调用率怎么从"时灵时不灵"变成稳定

做完工具之后实测发现，4B 模型经常「只说要做什么，却不真的调工具」（回答"好的，我来整理 D 盘"，
然后什么都不做）。原因不是工具写得不好，是**采样温度太高**：

| temperature | 真的调用工具 |
|---|---|
| 0.7 | 时灵时不灵（多次出现光说不做） |
| **0.4（现在）** | **6/6** |

另外还有两条经验：

1. **系统提示词里的人设会跟"当助手"打架**。最初的角色卡写着「有人求助时，先判断这件事对
   研究有没有价值」，结果让它整理文件，它回「抱歉，这与我的工作无关」。给 agent 用的人设
   必须显式写明「用户交代的事就是你的工作」，否则再好的工具也白搭。
2. **沙箱报错要写清"能用哪些目录"**。原来只回一句"路径越界"，模型就直接放弃了；
   改成把可用目录列出来之后，它会自己换个路径重试。

### "查了但不动手"：两道退回，外加一个会算结论的工具

2026-10-12 用户问"帮我检测一下为什么我的英伟达 FPS 显示是 N/A"，它跑了个 `nvidia-smi`，
然后从**进程列表**里推断"这些程序占用 GPU 导致 FPS 显示 N/A"—— 推理站不住，手也没动。
这一轮改了三处：

1. **新增 `gpu_check` 工具**。这类问题要看的不是"显卡自己那点信息"，而是
   哪块卡在带显示器、每个程序的显卡偏好、HAGS 开没开、叠加层进程在不在。
   顺带把每个程序被重复设置多次的记录去重了（原来那串长得能顶掉半页上下文）。
2. **结论在工具里算好，不让模型综合**。第一版把"怎么解读这份数据"写成提示放在工具输出里，
   结果 4B 模型把那几条**原样抄成了"可能的原因有四点"**，一条都没落到这台机器上。
   改成 Python 里判断拓扑（核显在带哪块屏、独显带哪块屏、叠加层在不在、HAGS 状态），
   输出第一行就是 `照这句说：…`，模型只负责复述。现在的实际输出：

   ```
   照这句说：这台是双显卡机器；有显示器是核显（Intel UHD）在带：2560x1600 @240Hz；
   另一路是独显直连：2560x1440 @143Hz；……显示的 N/A 就是这个原因——不是驱动坏了；
   能做的：① 控制中心切「独显直连」；② 在直连独显的显示器上玩；……
   剩下这些步骤只能你自己做：都是图形界面里的开关，命令行改不了，我也做不了；
   做完回游戏里开一次叠加层看帧数出不出来，就知道有没有好
   ```
3. **"只给建议"就退回去**。要是回复里出现「你可以尝试 / 建议你 / 需要你 / 手动」这类
   **建议腔**，而这条消息本身带"修"意（修复/解决/为什么/检测一下…），就把它退回去一次，
   要求二选一：① 能做的直接调工具做完；② 做不了就以「这一步只能你来做：」开头，
   说清是哪个界面里的哪个开关、为什么工具做不到、做完怎么验证。实测退一次不够
   （它还会再给一遍建议），所以允许退两次，再不行就让它说完。

   顺带把 `Restart-Computer`、`Stop-Computer`、`logoff` 加进了危险命令黑名单 ——
   既然在催它"动手"，就不能让它自己把电脑重启了。

agent 默认只能读文本文件。要看图片用 `see_image` 工具，它分两条腿：

**① 文字识别（离线、零依赖）** —— 调 Windows 自带的 OCR 引擎（`app/ocr_image.ps1`）。
你这台机器有 `zh-Hans-CN` 语言包，中文可用。关键经验：**先把图片放大再识别，准确率差别很大**。
同一张 900×300 测试图上的「阮·梅 本地 Agent 测试」那一行：

| 处理方式 | 识别结果 |
|---|---|
| 原图直读 | 阮 嗨 本 地 Agent 测 试 |
| 放大 2 倍 | 阮 · 梅 本 地 Agent 测 试 |
| 放大 3 倍 | 阮·梅本地 Agent 测试 |

所以 `ocr_image_file()` 会自动把图放大到高度 1200px（最多 3 倍）。深底浅字的图不用反色，
实测反色反而更差。另外 Windows OCR 会在汉字之间插空格，脚本会还原掉。

**② 画面描述（需要视觉模型）** —— 走 Ollama，装一个就有：

```
ollama pull qwen2.5vl:3b      # 3.2GB，中文最好
ollama pull moondream         # 1.7GB，更小更弱
```

装完不用改配置，`see_image` 会自动发现并使用。

### 让它真的产出文件：PPT / Word / Excel / 剪视频

库（python-pptx / python-docx / openpyxl / moviepy）早就装好了，但 agent 不会用 ——
你让它"做个 PPT"，它给你一段文字稿。**这里的关键决定是：不要让模型自己写 python 脚本。**
实测 4B 模型写的脚本十次有三四次跑不起来（漏 import、缩进错、路径是编的），
而且每次都要多花几十秒。改成"模型只输出 Markdown，排版交给固定代码"之后，成功率是 100%。

四个工具（都在 `app/office_tools.py`，注册在 `app/agent_server.py` 的 `TOOLS` 里）：

| 工具 | 用户怎么说 | 内容怎么写 |
|---|---|---|
| `make_pptx` | 做个 PPT / 演示 / 汇报 | `#` 开头的行是新的一页标题，`-` 是这一页的要点 |
| `make_docx` | 写个文档 / 报告 / 方案 | `#` 一级标题，`##` 二级，`-` 项目符号，`1.` 编号，`>` 引用 |
| `make_xlsx` | 做个表格 / 台账 / 预算表 | 每行一条记录，逗号或 Tab 分隔；第一行自动当表头；`#` 开头的行新建工作表 |
| `edit_video` | 剪一下 / 拼起来 / 抽音频 / 转 gif / 变速 / 静音 / 改分辨率 | `action` + `input`（多个用 `\|` 分隔）+ `output` |

几个刻意的设计：

* **封面不会被硬塞**。只有你给了标题，或者正文第一段本来就是"标题+副标题"的写法时才加封面；
  否则第一段直接当正文，免得同一句话既当封面又当第一页。
* **一页超过 8 条要点会自动拆页**，标题带「（1/2）」，不会挤成一坨。
* **忘了写扩展名会自动补**（传「汇报」也能出 `汇报.pptx`）。
* **拼接视频会自动统一分辨率和帧率**，遇到没有音轨的段落自动补静音 ——
  否则 ffmpeg 的 concat 会直接报错，而这是最常见的失败原因。

自检（两个脚本，改了工具之后都该跑一遍）：

```powershell
# ① 工具本身能不能用：真生成文件，再打开检查页数/行数/时长对不对（21 项）
D:\ai\envs\llm\python.exe scripts\smoke_office_tools.py

# ② 模型知不知道要用工具：把一句话丢给 ruanmei，看它会不会调对工具（3 个用例）
D:\ai\envs\llm\python.exe scripts\test_agent_office.py
```

实测结果（2026-10-11）：smoke 21/21 通过；端到端 3/3 都正确调用了对应工具，
例如"帮我做个 PPT，文件名 接口自检.pptx，两页"→ 真的调 `make_pptx` →
33 KB / 3 页（封面 + 两页，标题和要点都对）。

**改完要重启 7788 那个服务**（工具清单是启动时读进内存的）。

### 让 agent 能读工作目录外的图片

工作目录是沙箱，越界会被拒绝，而图片常常在别的盘。两个办法：

## 阶段 8：做成独立桌面应用（不用浏览器）

之前梅梅是靠"浏览器应用模式"打开的（`chrome.exe --app=...`），看着像应用，但本质还是浏览器，
任务栏里挂着 Chrome，而且必须装 Chrome/Edge。现在有第二条路：**WebView2**。

WebView2 是 Win10/11 自带的系统组件（Edge 的内核，但不用打开 Edge），`app/desktop.py`
把它嵌进一个普通窗口里 —— 界面还是那套网页，但已经是一个独立应用：自己的标题、图标、
任务栏按钮，没有地址栏，跟浏览器完全无关。

```powershell
# 直接跑（会自动把语音链路和应用服务拉起来，已经在跑的不会重复拉）
D:\ai\envs\llm\python.exe app\desktop.py

# 桌面上的「梅梅」快捷方式就是它（2026-10-12 起换成这个了），
# 用 pythonw 启动，连控制台窗口都没有
```

配套的几件小事：

* **双击第二下不会开出第二个窗口**。用 127.0.0.1:7791 当互斥锁，第二个实例会直接把
  已经开着的窗口拉到最前面（跟正常软件一样）。第一次启动要等两三秒，这期间再点一下也没事。
* **窗口自带的标题栏已经切成深色**。Windows 11 下传统 Win32 窗口（WinForms 就是）
  默认永远是浅色标题栏，哪怕系统是深色主题也不跟随，深色界面顶上顶着一条白的很扎眼；
  `desktop.py` 启动时会给自己的窗口调 `DwmSetWindowAttribute(20)`（旧系统退回 19），
  日志里会打印「标题栏已切成深色」。
* **没有控制台，就把输出接进 `logs\desktop.log`**；启动失败会弹一个框告诉你出错在哪一行，
  而不是默默什么都不发生。
* 旧的浏览器启动方式（`open_ruanmei.vbs` + `rm_app.ps1`）没删，挪到
  `archive\old-browser-launcher\` 了。想退回浏览器版，把这两个文件挪回来、
  再把快捷方式指回 `open_ruanmei.vbs` 即可。
* 真需要一个看得见报错的控制台窗口时，双击 toolkit 目录里的「启动阮梅.bat」（那条路没变）。

自查用的模式（**不用肉眼看界面**，跑完自动关窗并打印结果）：

```powershell
D:\ai\envs\llm\python.exe app\desktop.py --selftest --no-voice
# [窗口] 已允许网页使用麦克风
# [自检] 结果 = {"title":"梅梅 · 本地 Agent","ready":"complete","menuBtn":true,
#              "audioCtx":"running","storage":"ok","mic":"fail:NotAllowedError:..."}
```

实测（2026-10-11）：窗口正常打开、标题「梅梅」、进程只有 97MB（Chrome 那套要几百 MB）、
`audioCtx` 是 `running`（Web Audio 能播）、`storage` 是 `ok`（设备里的设置能留住，
靠 `private_mode=False` + `app/desktop-profile`）。

三个必须踩过去才知道的坑：

1. **WebView2 不会替网页回答"能不能用麦克风"**。宿主程序不处理就等于拒绝，
   所以 🎙 语音输入会直接失败。`desktop.py` 里挂了一个 `PermissionRequested` 事件，
   只放行麦克风和摄像头（不是无脑全放）。
2. **网页权限放行了，还有系统这一关**。实测这台机器上：

   | 位置 | 值 |
   |---|---|
   | `HKLM\...\CapabilityAccessManager\ConsentStore\microphone` | **Deny** ← 就是它 |
   | `HKCU\...\ConsentStore\microphone` | Allow |

   所以 `getUserMedia` 返回 `NotAllowedError: Permission denied by system`。
   **关键结论：这个拦截跟梅梅没关系，用无头 Edge 直接测（`scripts/check_mic.mjs`）
   报的是同一个错**，也就是说**「🎙 说话」在浏览器里本来也用不了**。
   修法两种：设置 → 隐私和安全性 → 麦克风 → 打开「麦克风访问 / 让应用访问你的麦克风 /
   让桌面应用访问你的麦克风」；或者以管理员身份运行 `修复麦克风权限.bat`（它只改这一个开关）。
   改完要把梅梅窗口完全关掉再开，权限只在启动时申请一次。
3. **localStorage 会丢**。pywebview 默认 `private_mode=True`，等于每次都以全新身份启动，
   语气、开关这些设置一个都存不住。要显式 `private_mode=False` + `storage_path=...`。

想调窗口本身（例如接 DevTools 看报错）：`app\desktop.py --debug`，会额外开一个
9223 的远程调试端口，量布局的脚本换个端口就能连它：

```powershell
$env:CDP_PORT = 9223
node scripts\check_layout.mjs http://127.0.0.1:7788/ 390 844
```

## 最后：什么时候不该微调

这三种情况，微调都是错的工具：

1. **你只有几十条数据** —— 效果不如把系统提示词写三遍
2. **你只是想让它知道某些事实** —— 那是 RAG 或系统提示词的活，微调会把它变成「大概记得」
3. **你只是嫌它回答风格不对** —— 先在 Modelfile 的 SYSTEM 里写清楚要求，往往就解决了

微调真正不可替代的场景只有一个：**你需要模型稳定地、以你特有的方式，完成某一类反复出现的任务**。除此之外，先试提示词和 RAG。
### 后端悄悄死掉 → 背景视频永远卡在最后一帧（2026-10-12 查清并修好）

用户报的症状是"背景卡住不动了"。查下来的链条是这样的：

1. 后端服务（7788 那个 `agent_server.py`）在 16:51 凭空消失：日志最后一行还是成功的请求，
   系统日志里没有崩溃记录，也没有 Python 堆栈 —— 像是被外部结束掉的。
2. 页面还开着，但背景视频是从后端**流式取**的。它当时刚换过素材（16:50 才切成 1080p），
   浏览器的缓存里只有一部分，要不到后面的数据就停在那一帧，**而且不会自己重试**。

复现方式（`scripts\check_video_recover.mjs`）：把网络限速到 150KB/s 让视频"边下边播"，
中途杀掉后端。结果和用户看到的一模一样：`paused=false`、`readyState=2`、
缓冲里其实已经有整段数据（缓冲到 32 秒 = 全片），但 `currentTime` 一动不动，
**既不触发 `stalled` 也不触发 `error`** —— 事件层面根本抓不到，这就是第一版重试逻辑没生效的原因。

四处修改：

| 层 | 做法 |
|---|---|
| 桌面窗口 | `watch_backend()` 每 6 秒探一次 7788，不在监听就重新拉起，并让页面 `location.reload()` |
| 页面 | `check()` 由 15 秒改成 8 秒一次；发现"刚才断过、现在好了"就重新拉外观配置，把背景重建一遍 |
| 视频 | 每秒对一次 `currentTime`：**连续 5 秒没往前走就重新挂一遍资源**（这才是真正治僵尸的那一招，从缓存重挂是一瞬间的事） |
| 朗读让路 | 加 60 秒上限：万一合成链路整个卡死，背景不会被按住一整天 |

实测（`check_video_recover.mjs` 的时间线）：后端被杀 → 视频在 10.7 秒冻住 →
**约 5 秒后自己从 0.6 秒重新播起来** → 提示条如实显示"后端没在运行（窗口进程会自动把它拉起来）" →
后端被看护拉回来后提示回到"就绪"，视频一路播到底。

### 用别的 App：`app` 工具

| action | 干什么 |
|---|---|
| `list` | 列出能启动的应用（系统清单，278 个） |
| `launch` | 按名字启动，如「剪映专业版」「计算器」 |

## "她一句话都没回"（2026-10-19 查清）

用户报：让她播放"我喜欢歌单"里的歌，一直没输出，怀疑崩了。

**服务没崩**，四个端口都在。日志里那次 `POST /api/agent` 是 14:26:46 进来的，
但直到 **14:29:06** 才出现第一次 `/api/tts` —— 中间 **140 秒没有任何输出**；
紧接着 14:29:07 那次 TTS 还返回了 **502**（`ruanmei:wry` 失败、回落默认语气也失败）。

**原因一：刚开机，语音模型还在预热。**
当天 14:25 才把整套拉起来，GPT-SoVITS（3GB）正在往显存里加载，跟 LLM、
背景视频抢同一块 GPU。事后再测：模型 16 token / 0.57 秒（27.9 tok/s）、
TTS 一句 3 秒，都正常 —— 所以这是**启动后头一两分钟的临时拥堵**，不是坏了。
（当时还有一个细节：整个生成花了 255 秒、TTS 花了 249 秒，两件事同时发生。）

**原因二（更关键，是我设计的问题）：文字是跟着语音出场的。**
流式朗读模式下，`asst.shown` 只在某一块音频**开始播放**时才推进。
于是语音一卡住，屏幕上就一个字都不显示 —— 看起来就是"她没回话"，
哪怕模型其实已经把文字产出来了。

修法：

* 前端给 `/api/tts` 加**硬超时**（120 秒，`AbortController`）—— 以前是无限等；
* 加**看门狗**：朗读开始后 8 秒还没有任何音频，就把已经拿到的文字先推出来，
  状态栏显示"语音还在准备…先把文字给你看"。实测（`scripts\check_text_watchdog.mjs`）：
  喂进文字、不给音频 → 3 秒/6 秒无反应，**9 秒时文字出现**，提示正确。

**顺带修了一个"撒谎"的毛病。** 实测问她「播放我喜欢歌单里的歌」，她既没调工具，
又回了一句"好的，我将为您播放您喜欢的歌单" —— 她做不到。这种不能靠提示词
（4B 模型会把工具说明原文念出来，或者直接编），所以改成**服务端判定**：

* `wants_specific_music()` 识别"点名要某首歌 / 某个歌单 / 某个歌手"
  （歌单、播放列表、收藏、一首、的歌、书名号…）；
* 命中就**直接如实回答**、不叫模型（0 秒），并给一条提示说明为什么；
* 标准答复由 `MUSIC_LIMITS_TEXT` 提供，`music(action=limits)` 也返回同一句。

实测：「播放我喜欢歌单里的歌」「放一首周杰伦的晴天」都是 0 秒如实回答；
「帮我放首歌」「把音乐暂停一下」「现在在放什么歌」仍走正常流程。

**给用户的建议**：先在 QQ音乐 里把「我喜欢」点开播起来，之后暂停/切歌/音量/看曲目
她都能接管；不指定歌单时说「放首歌」，她会接着放上次那首。

## 操作时弹黑框（PowerShell 窗口）—— 2026-10-13 修掉

用户报的现象：她用的时候会跳出一个 PowerShell 窗口。

**根因**：Windows 上从一个"没有控制台"的进程里起一个**控制台程序**
（`powershell.exe` / `cmd` / `tasklist` / `nvidia-smi` / `ffmpeg`），系统默认会给它
**开一个新的控制台窗口**。梅梅的服务进程本身就是用 `CREATE_NO_WINDOW` 拉起来的
（`desktop.py` 的 `start_background`），可它内部那十几处 `subprocess.run(...)`
**没带这个标志**，于是每次调用都要弹一个黑框。

**怎么抓到的**：用 `EnumWindows` 枚举可见的顶层窗口、每 250ms 采样一次，
边采样边触发操作。修复前抓到窗口标题正是
`C:\WINDOWS\System32\WindowsPowerShell\v1.0\powershell.exe`。
（注意：**不能用 `Get-Process | Where MainWindowHandle -ne 0` 判断** ——
控制台窗口属于 conhost，powershell 进程自己的 MainWindowHandle 是 0，这条路查不出来。）

**改法**：

* `agent_server.py` 顶部加了 `CREATE_NO_WINDOW` 常量和 `run_hidden()` 包装，
  然后把文件里 **10 处 `subprocess.run(` 全换成 `run_hidden(`**（顺手把两处
  `Popen` 也带上标志）；
* `voice/asr_server.py` 里那次 `ffmpeg` 调用也补上（按下 🎙 时它会转码，同样会弹）；
* 结论性的一条规矩：**这个项目里以后新增任何起子进程的代码，一律走 `run_hidden`。**

**验证**（同样的采样脚本）：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 问"现在在放什么歌"（服务端跑 powershell） | 抓到 `…\powershell.exe` 窗口 | — |
| 问"看看CPU和显卡状态"（powershell + nvidia-smi） | 抓到 | — |
| 🎙 语音识别（ASR 服务里跑 ffmpeg） | 会弹 | — |
| 双击「梅梅」冷启动（含拉起应用服务） | — | 60 秒采样 `NONE` |
| 三种操作连续触发 | — | 70 秒采样 `NONE` |

## 让她控制音乐播放（2026-10-13 加）

目标：说"放首歌 / 暂停 / 下一首 / 现在在放什么"，她能真的操作 QQ音乐。

**关键技术选择：走 Windows 的媒体会话（SMTC），不模拟按键。**
媒体键（`VK_MEDIA_PLAY_PAUSE`）只打到"当前活动会话"——QQ音乐 在后台、
或者你刚点过别的播放器时就不灵，而且我们没法知道它在放什么。
SMTC 是系统自己的会话表（就是 Win+G / 音量飞出里那个"正在播放"）：
能按应用名精确指定，也能反过来读出曲目，是一个正经的双向接口。

实现：`app/smtc.ps1`（PowerShell 调 WinRT 的
`GlobalSystemMediaTransportControlsSessionManager`）+ `agent_server.py`
里的 `music(action)` 工具。动作用 `TryPlayAsync / TryPauseAsync /
TrySkipNextAsync / TrySkipPreviousAsync`，音量用媒体键（`keybd_event`）。

这台机器上的实测（QQ音乐装在 `D:\夸克\QQ\QQMusic\QQMusic.exe`，
路径是从它自己注册的文件关联里读出来的，不是猜的）：

```
status → COUNT=1 APP=QQMusic.exe STATUS=Playing TITLE=夸张 ARTIST=周品 ALBUM=自我嘲弄
pause  → RESULT=True，AFTER_STATUS=Paused
play   → RESULT=True，AFTER_STATUS=Playing
```

端到端（经过模型）：说「现在在放什么歌？」「帮我放首歌」「把音乐暂停一下」，
她都正确调用了 `music`，并如实复述曲目。

三个踩过的坑：

* **PowerShell 脚本里不能有中文注释**。Windows PowerShell 5.1 按 ANSI 读 `.ps1`，
  带中文注释的文件直接解析失败（`Unexpected token ')'`）。这个项目的 `.bat`/`.ps1`
  一直要求 ASCII-only，这次又验证了一遍。
* **歌名乱码**。服务进程没有控制台，PowerShell 往管道写时用 OEM 代码页（GBK），
  python 按 UTF-8 解码就成了 `《????》`；同一个脚本在终端里跑却是正常的，很难查。
  改成**脚本写 UTF-8 文件、python 读文件**，绕开管道编码。
* **没有会话时自动拉起**：QQ音乐 没在跑就先启动它（等 12 秒）再执行动作，
  这样"放首歌"从冷启动也能用。

**按歌名/歌单点播（2026-10-19 加）**：QQ音乐 没有公开接口，也没注册 `qqmusic://`
这类 URL 协议，所以走 Windows UI 自动化（`uiautomation` 包）：

* 歌名：点搜索框 → `Ctrl+A` + `Delete` 清空 → 粘贴歌名 → 回车 → 按标题/歌手匹配 → 双击；
* 歌单：点左侧「喜欢·2905」这类条目 → 点「播放」；
* 服务端先解析「播放我喜欢歌单里的歌 / 放一首周杰伦的晴天」，直接调用，不经过 4B 模型，
  所以是 0 token、十几秒内出结果；失败（没登录、VIP、搜不到、界面改版）会如实说，不假装。

实测：`晴天` 选中周杰伦原版而不是翻唱；`喜欢` 歌单从《必杀技》开始放；
`zzzz不存在` 正确回落为标准失败答复。坑有两个：Windows PowerShell 5.1 的 UIA 读
QQ音乐 只返回 1 个节点，必须在 `D:\ai\envs\llm` 里用 `uiautomation`（已装）；
QQ音乐 的搜索框不接受 `ValuePattern.SetValue`，要用 `Ctrl+A` + `Delete` + 粘贴。
本地音频仍可走 `QQMusic.exe /play "文件路径"`（先把音乐目录加进「额外只读目录」）。

## 上下文预算与执行期风控（2026-10-20 加）

这轮不是加新工具，而是把"长对话 / 长期偏好"的成本和风险压下来：

* **历史裁剪**：`/api/agent` 先用 `approx_tokens()` 估 token，给 tools schema、
  人设和回复预留 2200 token，剩下的按"最近连续对话"保留；被丢掉的早期消息会在前端
  提示「已省略 X 条」，不会静默截断。
* **习惯按需注入**：`data/习惯.md` 仍用 Markdown（`##`/`###`）维护，但
  `habits_for_prompt(user_msg)` 只挑本轮相关的小节（剪视频 / 语音 / 界面 / 作息 /
  吃饭 / 音乐…），"干活的方式"永远保留；挑不到才回退整份，单次上限 1400 字。
  习惯文件长大后不会每轮全塞进 context。
* **执行期闸门**：保留原生 function calling（Ollama 的 `tools` + 工具结果回灌循环），
  不额外做两轮规划器；把闸放在执行前：`del/rmdir/taskkill/reg add/winget uninstall`
  等高风险命令、`install_app(action=install)` 和 `app(action=close)` 都要用户明确
  确认才执行。省掉一次完整 LLM 往返，又不让 4B 模型自己按下去。

实测：30 条长历史会提示省略 12 条并正常回答；`del test.txt` 未确认时返回
`[需要确认]`；剪视频 / 作息 / 音乐三类问题分别只注入对应小节。

这条思路对应"离线清洗/结构化、按需注入、执行期风控"：检索相关性和叙事一致性是
两件事，不能指望 attention mask 或一次检索自动解决。

## 日常规划表（2026-10-12 加）

用户问"她能不能帮我写日常规划表"。先照老规矩测了一遍，发现两个问题，都修了：

**问题一：好话被自己的规则挡了。** 一句"帮我写一份日常规划表"被"该查不查"那条规则

结果调了 `system_info`，最后答出来的是 **CPU 使用率和显卡温度**。修法：

* `LOOK_WORDS` 里删掉「帮我」「怎么」「打开」这类泛词，只留下真正"去看现象"的说法；
* 新增 `MAKE_WORDS`（写一份/做一份/规划表/清单/方案/ppt…）：命中就直接放行，
  **不**触发"该查不查"；
* 那条退回提示也补了逃生口："如果你判断他要的其实是产出一份东西，就别乱调工具、直接做"。

**问题二：表是出来了，内容不行。** 它把"7:30 起 / 8:30 到公司 / 18:00 下班"原样抄成
一行表格就交差了 —— 4B 模型不擅长"按约束生成结构化排程"。还是那句老经验：
**结构算在代码里，模型只负责收集参数**。于是加了 `make_dayplan` 工具
（实现在 `app/office_tools.py` 的 `build_dayplan()`）：

* 骨架由它算：起床→早饭→通勤→上午→午休(12:00–13:30)→下午→下班+通勤→晚饭→自由时间→洗漱→睡觉；
  通勤时间是反推的（出门 = 到岗 − 单程时长），还会处理"起得比出门还晚"这种矛盾约束；
* 用户另外交代的固定安排（`extras`，每行一条，如「20:00 健身」）会**按时间插到正确位置**，
  认不出时间的就放表尾「随时要做的」；
* 参数不够时先问：`habits_life_empty()` 检查「生活习惯」那几节是不是空的，空着就在
  系统提示里加一句"先问清起床、通勤、固定安排、晚上几点停再排，别凭空编"。

实测（同一句话，改之前 vs 改之后）：

| | 改之前 | 改之后 |
|---|---|---|
| 只给"帮我写一份日常规划表" | 被退回，调 `system_info`，答 CPU/显卡 | 不乱调工具，直接问清三个必要信息 |
| 给了作息约束 | 生成 1 行表格（把输入抄了一遍） | 调 `make_dayplan` → 11 个时段的真实时间表，5.7KB |

### 上课日：套"上班族模板"是错的（2026-10-12 补）

拿到真实作息（凌晨 1–4 点不定时睡、有课就比上课时间早半小时起、12:30 下课、
午饭+午睡 2–3 小时、15:30 上课约 2 小时、晚饭半小时、之后自由活动/健身）之后，
用原来那个 `build_dayplan`（起床→通勤→朝九晚五→下班）一套，出来的时间全是错的 ——
它的 12:00 午饭、13:30 上班是写死的，跟"12:30 下课、15:30 才上下一节"对不上。

于是加了 `build_study_plan()`（`make_dayplan` 里带 `classes` 参数就走这条路）：

* 骨架是 **课表 + 空档 + 大块自由时间**，不是朝九晚五；
* 起床 = 第一节课 − `wake_before`（默认 30 分钟）；午饭+午睡接在上午最后一节后面；
  晚饭接在傍晚那节后面；剩下的到睡觉前算自由活动；
* 课与课之间 ≥20 分钟的空档单独列出来，**但要先扣掉午饭/晚饭占掉的那段** ——
  实测踩过：12:30 下课、15:30 上下一节，直接算会冒出一个"12:30–15:30 空档"，
  跟"12:30–15:00 午饭+午睡"整块重叠，表自相矛盾。

实测（10:30–12:30 + 15:30–17:30 两节课）：

```

10:30–12:30  上课
12:30–15:00  午饭 + 午睡
15:00–15:30  空档
15:30–17:30  上课
17:30–18:00  晚饭
18:00–01:00  自由活动（健身按路上+训练 2.5 小时算；不然游戏/学习）

```

顺带把作息写进了 `data\习惯.md` 的「生活习惯 / 作息 / 吃饭 / 娱乐」三节 ——
以后排表不用再问一遍，聊天时也会照这个来。

## 定时提醒 + 唤醒词（2026-10-12 加）

### 到点她自己出声提醒

数据在 `data\提醒.json`，调度线程跑在 agent_server 里（每 20 秒看一次表）。
到点的动作是：**服务端直接向本地 TTS 要一段 wav，再用 PowerShell 的
`Media.SoundPlayer` 从这台机器的音箱放出来** —— 不依赖页面开着（页面关了、
窗口最小化都会响），这才是"日用"。

提醒条目的字段：`time`（HH:MM）、`repeat`（daily / weekdays / weekly / once）、
`days`（weekly 用，1=周一）、`date`（once 用）、`enabled`、`last_fired`。

几个刻意的设计：

* **错过就不补**。判定窗口是"到点后 90 秒内"，超过就算错过 —— 否则关机或睡眠一整晚，
  第二天开机时所有积压的提醒会一次性全念出来。
* **`last_fired` 去重**：同一分钟内不会重复响；`once` 响过自动置 `enabled=false`。
* 工具 `remind(action=add/list/delete)` 让梅梅自己排；提示词里写明
  "这是一次性排程，**不要**用 remember 去记它"，免得两种"记住"混在一起。

实测：用 `action=test` 立刻试听一句 → 返回「念出来了」（合成 + 播放共用 23 秒，
第一次含模型预热）；再排一条 1 分钟后的一次性提醒，到点后记录里出现
`{"at":"2026-10-12 17:44","text":"自检测试：到点了","ok":true}`，条目自动
`enabled=false`、`last_fired` 落上时间戳。测试数据事后都清掉了。

### 唤醒词「亲爱的」

说到「亲爱的」就是在叫梅梅。实现放在**发送入口**（打字和语音输入都走这条路，行为一致）：

* 只叫一声（后面没别的要求）→ **不打模型**，直接答应一句（"在的，你说。"之类，随机），
  用她的声音读出来。实测：打模型 **0** 次。
* 后面带了要求 → 照常走完整流程。实测：打模型 **1** 次，答案正常。
* 服务端额外插一句系统提示，说明"这是主人在点你的名"，免得模型把「亲爱的」理解成
  "用户在自称亲爱的"（她在人设里本来就管主人叫亲爱的，这两种含义很容易混）。

注意：现在这条只覆盖"你对着输入框说/打"，**不是**全程监听麦克风的唤醒词 ——
那种要一直录、一直跑识别（费资源，而且你机器上的麦克风权限还没打开）。
真要做常驻唤醒，得加 VAD + 连续识别，说一声我再做。

## 让它记住你的习惯（2026-10-12 加）

想让它记住"剪视频的习惯""做 PPT 的习惯"这类东西，做法是**一个 Markdown 文件 + 每轮读一遍**：

```
C:\Users\qqqqq\Documents\Codex\2026-10-06\wo\outputs\local-ai-toolkit\data\习惯.md
```

* 每轮对话都会把它的内容作为一条 `system` 消息塞在对话最前面，所以**改完立刻生效**——
  不用重新 `ollama create`，也不去动角色人设那份提示词（两件事分开，互不打架）。
* 两个工具给它用：`remember(text, section)` 记一条、`forget(keyword)` 删一条。
  提示词里写清了什么时候该记：他说「以后都这样 / 记住 / 我喜欢这样」这类**面向以后**的话，
  或者同一件事纠错两次以上；**一次性的临时要求不记**。
* 你也可以直接打开这个文件编辑；界面右上角「外观」面板底部也有一个编辑器
  （读取/整份保存，`GET/POST /api/habits`）。
* 注入时会剪到 1800 字以内（保留头尾），免得习惯越攒越多把上下文挤爆。

实测：先把剪视频的三条写进文件，问"我剪视频的习惯是什么"→ 它照着答对了；
再说"记住：以后做 PPT 都用深色主题，每页要点不超过 5 条"→ 它调用 `remember`，
文件里出现 `## 做PPT` 那一节；再问"我做 PPT 的习惯是什么"→ 答"用深色主题，每页要点不超过 5 条"。

设计上的取舍：

| 做法 | 为什么这么选 |
|---|---|
| 单独一个文件，不写进 Modelfile | 改一行立刻生效，不用重训/重建模型；也方便你手改、备份、清空 |
| 每轮注入，不做向量检索 | 习惯是**少量、长期、每轮都该生效**的东西，全量塞进去最简单也最可靠；要记几百条再说检索 |
| 限定 1800 字 | 4B 模型上下文只有 8192，习惯不该把工具说明和对话挤出去 |

### 生活习惯也在同一份文件里（2026-10-12 补）

文件里有一个 `## 生活习惯` 大节，下面六个小节：**作息 / 吃饭 / 出门与通勤 / 健康 /
花钱与购物 / 娱乐**。空着没关系 —— 日常对话里说「我一般…」「我习惯…」，它会用
`remember` 记到对应的小节里（小节的井号个数是 `###`，所以 `habits_add()` 找标题时
按"名字对得上"匹配，不写死 `##`）。

注入给模型的系统消息里额外写明了两件事：**生活类的话要记**、以及**只记面向以后的**
（"今天几点出门"这种一次性安排不记）。

实测：说「记住：我出门基本都坐地铁，能不打车就不打车」→ 它自己选了
`section="出门与通勤"`；说「我一般 12 点前就睡了」→ 选了 `section="作息"`；
两次都正确落进了对应小节。测试用的那两条假数据后来都用 `forget` 删干净了。

想让它按作息**主动提醒**你（几点该睡了、周几有课），那是"定时任务"能力，现在还没有 ——
现有的自动化只在 Codex 这一层，梅梅自己不会到点主动说话。要的话可以再给它加。

### 一个把我骗了半小时的坑：旧的服务进程还在监听

改完 `agent_server.py` 之后，我用同样的方式重启服务、跑测试，结果"改动没生效"。
真相是：**正在监听 7788 的还是改动之前那个进程**，我新起的那个因为端口被占直接
`bind()` 失败退出了（`logs\agent_server.log` 里只有一串 Traceback，不会主动告诉你）。

要确认自己测的是新代码，用这两条对一下时间：

```powershell
$p = (Get-NetTCPConnection -State Listen -LocalPort 7788).OwningProcess
Get-Process -Id $p | Select-Object Id, StartTime
(Get-Item app\agent_server.py).LastWriteTime          # StartTime 必须晚于这个
```

顺便说：窗口进程里的看护线程会在端口没人监听时自己拉一个 —— 这也是为什么会出现
"两个实例、一个绑不上"的情况。

## 换背景 / 换图标

界面右上角「外观」里能换背景（图片或视频）和图标，改完立刻生效、不用重启服务。
三种来源都行：

### 三块"面板"的不透明度是分开调的（2026-10-12 加）

背景一旦亮起来（比如 4K 视频 + 背景明暗拉到 5），盖在它上面的三块半透明面板就会"发白"、
文字看不清。所以外观面板里现在有三个滑块：

| 滑块 | 管哪儿 | 说明 |
|---|---|---|
| **左栏不透明度** | 左侧会话栏 | 100 = 实心板子；调小背景透进来。默认 78 |
| **底部输入区不透明度** | 最下面那条输入栏 | 同上 |
| **顶栏不透明度** | 顶部标题条 | 拉满就没有那层白蒙蒙 |

顺带把侧栏那两个滑块的分工理顺了：以前只有一个「边栏融入背景」，拉到 100 时左边边缘的
alpha 会被算成 **0**，整条侧栏被背景顶掉、字完全看不清 —— 这就是"边栏被遮挡"的原因。
现在 **左栏不透明度是主控**（右边缘用这个值），而「融入背景」只负责背景露出多少、糊多少，
以及让左边缘比右边缘再透一点（保留"融进背景"的过渡感）。实测 blend=100 / 左栏 92 时：
左边缘 alpha 0.74、右边缘 0.98，列表文字清楚，背景也还看得见。

另外修了个连带 bug：`/api/appearance` 保存时重建配置字典，**漏掉了 `extra_read`**，
于是每次改背景都会把「额外只读目录」清空。现在会原样带上。

背景视频现在有三份可选（外观面板的「背景」下拉里都能选，都是从同一段 4K 母带压的）：

| 文件 | 参数 | 大小 | 什么时候用 |
|---|---|---|---|
| `《崩坏 星穹铁道》- 阮梅 4k.mp4` | 3840×2160 / 120fps / 40Mbps | 156MB | 想要最清晰；但主背景 + 侧栏副本是**两份同时在解码**，笔记本上会明显发热、甚至卡住 |
| `阮梅-背景-2560x1440-60fps.mp4` | 2560×1440 / 60fps / 4Mbps | 16MB | 屏幕大、想留一点清晰度余量的时候 |
| `阮梅-背景-1920x1080-60fps.mp4` | 1920×1080 / 60fps / 2.6Mbps | 10.6MB | **现在用的这个**。最省，解码负载大约是 4K 那份的 1/8 |

三份都是 `-g 120`（每 2 秒一个关键帧）+ `+faststart`，循环和拖动才不会卡一下；
音频全部去掉（背景本来就静音）。

循环还加了兜底：`loop` 属性只是"请求浏览器循环"，实测解码一跟不上就会停在最后一帧，
所以 `loopGuard()` 另外挂了 `ended`（手动绕回 0 继续放）和 `pause`/`stalled`（该播就重新
`play()`，并且只在窗口可见时抢，避免最小化的时候反复唤醒解码）。

两个当时踩到的坑，现在都修了（2026-10-12）：

| 症状 | 原因 | 现在的行为 |
|---|---|---|
| 背景选了个视频，界面一片黑，`<video>` 元素在但 `readyState` 是 0 | 素材名里带中文/空格，浏览器请求时是 `%XX` 编码的，而静态资源那段代码**没做 URL 解码**，于是每个请求都 404 | 请求路径先 `unquote` 再查文件；顺带加了"必须落在 assets 目录内"的校验 |
| 放 150MB 的视频，内存飙升、拖进度条就断 | 原来是把整个请求区间一次性读进内存再吐出 | 改成 256KB 分块往外写，并且正确处理 `Range`（返回 206 + `Content-Range`） |

想确认外观到底生效没有（不用肉眼看），有个脚本：

